# 命名规范与一致性治理

> 状态：正式规范
> 目标：开发者仅凭常识和本文档就能正确命名新代码

---

## 一、核心原则

1. **单一语义**：每个业务名词在全系统保持唯一含义
2. **全链路对齐**：`领域语义 → 后端包 → API路径 → 前端feature → 前端路由`
3. **最小惊讶**：目录名、文件名、URL 看一眼就能对应

---

## 二、业务名词表

| 名词             | 定义                     | 使用场景               |
| ---------------- | ------------------------ | ---------------------- |
| **me**           | 当前登录用户（第一人称） | 个人看板、个人设置     |
| **member**       | 组织成员（第三人称）     | 组织管理、成员列表     |
| **billing**      | 计费系统                 | 钱包、充值、发票、订阅 |
| **budget**       | 预算管理                 | 资源分配、费用控制     |
| **notification** | 系统通知                 | 消息推送               |
| **approval**     | 审批                     | 审批流程               |

> "钱包管理"是 billing 的 UI 文案标签；代码、API、URL 路径统一用 `billing`（无需要特殊处理的例外）。

---

## 三、命名风格速查

| 层级              | 风格                     | 示例                                                  |
| ----------------- | ------------------------ | ----------------------------------------------------- |
| Go 包名           | 全小写单数               | `domain/notification`, `handler/budget`               |
| Go 文件名         | snake_case               | `platform_key_create.go`                              |
| API 路由前缀      | 领域单数；集合资源可复数 | `/budget`, `/notifications`, `/approvals`             |
| 前端 feature 目录 | kebab-case               | `features/billing/`, `features/mydashboard/`          |
| 前端 API 文件     | 与 feature 目录同名      | `api/billing.ts`, `api/notifications.ts`              |
| 前端 API 导出     | `{domain}Api` camelCase  | `billingApi`, `notificationApi`                       |
| 前端 route 目录   | 与 URL 路径对齐          | `routes/billing/` → `/billing`, `routes/me/` → `/me/*` |
| 前端 query-key    | feature 领域名           | `['billing', ...]`, `['mydashboard', ...]`            |
| 权限 key          | `{domain}:{action}`      | `budget:read`, `org:manage`                           |
| 前端权限常量      | UPPER_SNAKE_CASE         | `BUDGET_READ`, `ORG_MEMBERS`                          |

| -------- | ------------ | ---------------- | --------------------- | ---------------- | -------------- | ------------ |
| 组织     | org          | `/org`           | org                   | routes/org       | `/org/*`       | `org:`       |

| 密钥     | keys         | `/keys`          | keys                  | routes/keys      | `/keys/*`      | `keys:`      |
| 模型     | models       | `/models`        | models                | routes/models    | `/models/*`    | `model:`     |
| 仪表盘   | dashboard    | `/dashboard`     | dashboard             | routes/dashboard | `/dashboard/*` | `dashboard:` |
| 审计     | audit        | `/audit`         | audit                 | routes/audit     | `/audit/*`     | `audit:`     |

## 五、单复数约定

- **领域命名空间**用单数：`/budget`, `/org`, `/me`
- **集合资源**用复数：`/notifications`, `/approvals`
- **例外**：`keys`, `models` 作为领域名时保持复数

判断方法：路由本身代表一个"领域入口"就用单数，代表一组同类实体列表就用复数。

## 六、特殊情况处理

### 6.1 me 领域拆分

当前用户相关功能拆为两个 feature：

- `mydashboard`：个人看板、使用统计
- `account`：个人设置、密码

共享路由前缀 `/me/*`，route 目录统一放 `routes/me/`。

---

## 七、新增领域检查清单

新增业务领域时，逐项确认：

- [ ] 领域名词是否有明确、单一的定义？与现有名词是否冲突？
- [ ] Go domain 包名确定：`domain/{name}`（小写单数）
- [ ] Go handler 包名确定：`handler/{name}`（小写单数）
- [ ] API 路由前缀确定：单数 or 复数
- [ ] 前端 feature 目录：`features/{name}/`
- [ ] 前端 API 文件：`api/{name}.ts`（与 feature 同名）
- [ ] 前端 route 目录：`routes/{url-prefix}/`（与 URL 对齐）
- [ ] 导出名：`{name}Api` camelCase
- [ ] Query keys：以领域名为 namespace
- [ ] 权限 key：`{domain}:{action}`

---

## 八、代码审查检查点

Review 时必须验证：

1. `routes/{x}/` 对应的 URL 是 `/x/*` 还是有特殊映射？有则确认在本文映射表中已记录
2. `api/{x}.ts` 与 `features/{x}/` 是否同名
3. 新代码是否把 `member` 误用于"当前用户"语义（应为 `me`/`mydashboard`）
4. 新增领域是否走过检查清单
