# 月度预算管理 — 页面设计

## 背景

当前预算管理页面是"总配置"视角：左树选部门，右侧编辑该部门的总额度 / 预留池 / 成员额度 / 项目。**没有时间维度的操控感**——用户无法直觉地感知"这是哪个月的预算"、"下个月预算改不改"、"上月花了多少"。

截图中已有 `period` 字段、前端 `shiftBudgetPeriod()` 工具和后端 `budget_consumed` 的 period_key 机制，说明**技术侧已具备月度基础设施**，但页面还没充分利用它。

---

## 设计目标

| # | 目标 | 衡量标准 |
|---|------|----------|
| 1 | **月度切换零迷茫** | 用户 3 秒内看懂当前月份、知道如何切月 |
| 2 | **预配下月** | 可提前为下月设置额度分配，无需等到月初手忙脚乱 |
| 3 | **回顾往月** | 只读浏览历史月份的分配 & 消耗快照 |
| 4 | **本月可调** | 当月预算可随时调整（业务场景：临时加量、紧急冻结） |
| 5 | **最小改动** | 复用现有树面板 + 详情面板，增量叠加月度控件 |

---

## 核心交互概念

```
┌──────────────────────────────────────────────────────────────────────┐
│ 顶部 Period Bar                                                       │
│  ◀  2026年8月（本月）  ▶      [ 预配下月 ]                            │
├────────────┬─────────────────────────────────────────────────────────┤
│ 部门树     │  详情面板（与 Period 上下文绑定）                         │
│            │                                                          │
│ (现有)     │  Summary Cards + 消耗进度 + 项目 + 成员额度              │
│            │                                                          │
└────────────┴─────────────────────────────────────────────────────────┘
```

**一句话：在现有页面顶部加一条 Period Bar，所有下方内容随 period 切换而联动。**

## Period Bar 设计

### 三种月份状态

| 状态 | 表现 | 操作权限 |
|------|------|----------|
| **过去月份**（已结束） | 灰色标签 "已结束"；数据只读 | 仅浏览，编辑按钮全部禁用 |
| **当前月份** | 蓝色标签 "本月"；正常编辑 | 完全可编辑（调整额度 / 新建项目 / 改成员配额） |
| **下一月份**（预配） | 橙色标签 "预配中"；可编辑 | 可编辑分配配置；consumed 显示 "—"（尚无消耗） |

### 交互细节

- **左右箭头切换月份**，range 限制：最早 = 公司首次有预算记录月，最晚 = 当前月 + 1（下月）。
- 点击月份文字弹出 date picker（月份级别），方便跳远。
- "预配下月"按钮仅在"本月"视图时显示，一键跳到下月并进入编辑态。
- 切月时左侧树选中状态**保持**（同一部门跨月查看）。

## 下月预配 — 工作流

### 动机

管理员每月底提前规划下月预算。可能要根据本月使用量做微调。

### 流程

```
1. 点击 "预配下月" 或切换到 M+1
2. 系统检查下月是否已有分配记录
   ├── 无记录 → 显示 "继承本月配置" 提示 + [一键继承] 按钮
   └── 有记录 → 直接展示下月分配
3. 用户在下月 period 下编辑已有实体的额度（部门 / 成员 / 项目的数字）
4. 编辑即时保存（与当前月行为一致）
5. 下月 1 日到来时，系统自动以下月配置为当月 budget 使用
```

> **注意**：下月预配只能修改已有实体的预算数字，不能新建/删除部门、成员或项目。新建操作需在当月完成（因为实体依赖主表 FK）。

### "一键继承" 的语义

- 将当前月的 `budget`、`reservedPool`、`personal_budget`、项目 budget **复制**到下月 period 的分配记录。
- consumed 全部初始化为 0。
- 继承后用户可逐项微调。

### 未预配时的缺省行为

如果管理员**未**手动预配下月，系统自动沿用上月分配配置（零 consumed）。这保证业务不中断——预配是锦上添花，非必须动作。

---

## 往月回顾 — 只读视图

切到 M-n 月份时：

- Period Bar 高亮 "已结束" 标签。
- 所有编辑按钮替换为 disabled 态或直接隐藏。
- Summary Cards 展示该月**最终**分配 + 最终消耗。
- 消耗进度条按实际值渲染（不动态变化）。
- 成员额度列表展示该月分配值 + 当月消耗。

> 页面不提供"修改历史月份"能力——已结束的账期不可篡改。

---

## 本月调整

**当月只允许上调，不允许下调。** 理由：月中突然缩减预算会导致正在使用的成员立即被拦截，引发业务中断和工单。下调通过"下月预配"提前生效，给团队缓冲期。

前端实现：编辑框校验 `newValue >= currentValue`，小于时 disabled 确认按钮，提示"当月预算仅可上调。如需缩减，请配置下月预算。"

## 下月预配 — 下调分配策略

### 问题场景

管理员要把下月部门预算从 ¥100 降到 ¥60。继承过来的分配是：子部门 ¥20 + 项目 ¥30 + 成员额度 ¥20 + 预留池 ¥10 = ¥80。新预算 ¥60 无法容纳全部分配，缺口 ¥20 需要从子项中释放。

### 行业常见策略

| 策略 | 做法 | 优点 | 缺点 | 代表 |
|------|------|------|------|------|
| **等比缩减 (Peanut Butter)** | 所有子项按相同比例缩减 | 公平、可解释、无需判断优先级 | 不区分重要性，可能砍到关键项目 | 传统企业预算、AWS Budget Actions |
| **优先级削减** | 预定义优先级，从低优先级开始砍 | 保护核心业务 | 需要事先标注优先级，管理成本高 | McKinsey 推荐的战略缩减 |
| **基于使用量保护** | 上月使用率高的少砍，使用率低的多砍 | 数据驱动，贴合实际需求 | 惩罚节约者，可能鼓励"花完额度" | FinOps / Cloud Cost Allocation |
| **先砍预留池** | 预留池优先清零，再等比砍其他 | 预留池本就是缓冲区 | 可能不够填缺口 | 常识做法 |
| **管理员手动** | 系统只提示缺口，管理员逐项调整 | 最灵活 | 操作繁琐 | 多数 B2B 产品初期做法 |

### 推荐策略：先吃预留池 → 等比缩减 + 手动覆盖

综合考虑：

1. **产品定位**：TokenJoy 是管控平台，用户是企业管理员，对预算调整有判断力。
2. **数据结构**：现有模型天然有预留池（缓冲）、子部门、项目、成员四个层级。
3. **MVP 原则**：不引入优先级标签系统（YAGNI）。

**推荐分三层递进：**

```
缩减缺口 = 旧总分配 - 新预算

Step 1: 先吃预留池
  实际缩减 = min(缺口, 预留池)
  缺口 -= 实际缩减
  预留池 -= 实际缩减

Step 2: 等比缩减剩余子项
  if 缺口 > 0:
    ratio = (总分配 - 预留池已扣 - 缺口) / (总分配 - 预留池已扣)
    子部门.budget *= ratio
    项目.budget *= ratio  
    成员额度 *= ratio（通过人均额度批量调）
    // ratio 保证所有人同比例承担，公平透明

Step 3: 管理员手动微调
  系统展示等比缩减后的分配预览
  管理员可逐项覆盖（只要总和 ≤ 新预算）
```

### 交互流程

```
┌─────────────────────────────────────────────────────────────────┐
│ 下月预算编辑                                                      │
│                                                                   │
│ 部门总预算  [¥100] → [¥60]                                       │
│                                                                   │
│ ⚠ 新预算低于已分配 ¥80，需缩减 ¥20                               │
│                                                                   │
│ 建议分配方案：                                                    │
│ ┌───────────────────────────────────────────────────────────┐    │
│ │ 项目            原值      建议值     手动调整              │    │
│ │ ─────────────────────────────────────────────────────────  │    │
│ │ 预留池          ¥10       ¥0        [    0   ]            │    │
│ │ 子部门额度      ¥20       ¥17       [ 17.14  ]            │    │
│ │ 项目预算        ¥30       ¥26       [ 25.71  ]            │    │
│ │ 成员额度        ¥20       ¥17       [ 17.14  ]            │    │
│ │ ─────────────────────────────────────────────────────────  │    │
│ │ 合计                      ¥60       ¥60 ✓                 │    │
│ └───────────────────────────────────────────────────────────┘    │
│                                                                   │
│ 💡 预留池已优先清零释放 ¥10；剩余 ¥10 按原比例分摊               │
│                                                                   │
│                    [取消]  [应用此方案]  [我自己调]               │
└─────────────────────────────────────────────────────────────────┘
```

**三个出口：**
- **应用此方案**：系统自动写入建议值。
- **我自己调**：跳过自动计算，进入正常编辑模式（管理员手动改每项）。
- **取消**：放弃下调。

### 为什么不用"基于使用量"策略

看起来很聪明，但有两个问题：
1. 下月的 consumed 是 0（还没开始），没有"下月使用量"可参考。用上月使用量做依据会惩罚节约型团队。
2. 增加认知负担——管理员得理解"为什么 A 被砍 30% 而 B 只砍 10%"。等比缩减的解释成本是零。

### 为什么不做优先级

需要管理员事先给每个子部门 / 项目标优先级。这是额外的管理负担。等用户量上来后如果有需求再加——先用等比缩减 + 手动覆盖覆盖 90% 场景。

### 边界处理

| 场景 | 处理 |
|------|------|
| 等比缩减后某项 < 0 | floor 到 0，缺口分摊给其他项 |
| 等比缩减后成员额度 < 已分配 Key 额度 | 系统提醒："部分成员 Key 额度超出新个人额度，下月生效后相关 Key 将被限制" |
| 只缩减预留池就够了 | 不触发等比缩减面板，直接展示"预留池从 ¥10 → ¥0，其他不变" |
| 缩减到 0 | 允许。意味着下月该部门暂停使用 |
| 子部门有自己的子分配超出缩减后额度 | 级联校验：警告"子部门 X 的内部分配超出新额度，需同步调整" |

## 页面布局细化

### Period Bar 组件

```
┌─────────────────────────────────────────────────────────────────┐
│ ◀   [2026年8月]（本月 🔵）  ▶         ┊  [ 预配下月 →]          │
└─────────────────────────────────────────────────────────────────┘
```

- 高度 48px，粘顶（sticky），与面包屑同行或紧随其下。
- 月份标签 + 状态 badge 居中偏左。
- "预配下月" CTA 居右，仅当前月可见。
- 箭头 hover 显示目标月份文字（tooltip）。

### Summary Cards 升级

现有三张卡片（总额度 / 已分配 / 预留池）之外，增加第四张：

| 总额度 | 已分配 | 预留池 | 本月消耗 |
|--------|--------|--------|----------|
| ¥100   | ¥60    | ¥10    | ¥32 / ¥100 (32%) |

- 第四张卡在**过去月份**变为"当月消耗"（终值）。
- 在**下月预配**中变为"预计消耗 —"（暂无数据）。

### 消耗进度条

- 当前月：实时刷新的进度。
- 过去月：定格终值。
- 下月：进度条置灰，显示 "尚未开始"。

## 边界情况

| 场景 | 处理 |
|------|------|
| 公司刚注册，无历史月份 | 左箭头 disabled；仅展示当月 |
| 下月已有预配，再点"一键继承" | 弹确认框："下月已有配置，覆盖后不可恢复。确认继承？" |
| 月中新增部门 | 新部门在当月 + 下月预配中可见，历史月快照中不存在 |
| 账期切换日（月初零点） | 前端定时刷新 `getCurrentBudgetPeriod()`，切月后 Period Bar 自动更新标签 |
| ~~固定账期~~ | 当前 `org_nodes.period` 只支持 `'monthly'`（CHECK 约束），固定账期为未来特性，暂不考虑 |

---

## 不做什么

- **不做** 跨月对比图表（属于 dashboard / 报表，不是预算管理页的职责）。
- **不做** 自动预算建议 / AI 推荐额度（YAGNI）。
- **不做** 批量月份编辑（一次只编辑一个月份的配置）。
- **不做** 预算审批流（当前预算修改即时生效，审批是 approval 引擎的事）。

---

## 实现优先级

| Phase | 内容 | 价值 |
|-------|------|------|
| P0 | Period Bar + 月份切换 + 只读历史 | 用户能回顾和理解月度维度 |
| P1 | 下月预配编辑 + 一键继承 | 提前规划，月初无缝切换 |
| P2 | 本月调整 toast 提醒 + 固定账期兼容 | 边界完善 |

## 视觉参考

基于截图现有风格（白底卡片、左树右详情、蓝色 accent），新增元素最小化：
