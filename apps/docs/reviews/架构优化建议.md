# 架构优化建议

> 基于对 `apps/backend`、`apps/frontend` 现有代码与 `apps/docs/` 全部架构文档的核对整理。  
> 只列**已确认**的问题（均已读代码验证），不臆测。按影响范围排序：先讲并发/一致性，再讲可观测性，最后讲工程卫生。

---

## 1. 总体评价

架构整体是健康的：分层清晰（`http → domain → store`）、组合根集中在 `internal/app/`、Store 接口收敛、River 统一了异步任务、`SUPPORT_SAAS` 单一 flag 切换两种部署形态而不拆分代码。这些是好的基础，下面的建议都是在这个基础上的局部改进，不涉及推倒重来。

---

## 2. 并发与数据一致性

### 2.1 Platform Key 直接创建路径缺事务保护

`domain/keys/platform_key_create.go` 的 `CreatePlatformKey`：读预算 → 写 DB（无锁）→ 调 NewAPI Admin API → 失败无补偿。对比审批流程创建 Key（`approval_handler.go` 的 `OnApprovedTx`）已经有 `AcquireBudgetLock` + `PostApprove` + `Compensate` 三段式保护，两条路径创建同一种资源却是两套并发安全等级。

**建议**：把直接创建路径也套进事务 + advisory lock，或者干脆让"直接创建"复用审批引擎的 `OnApprovedTx`/`Compensate` 骨架（审批引擎本质上就是"创建+补偿"的通用状态机，没有理由不能给非审批场景复用）。

### 2.2 审批预算校验的静默 clamp

`KeyApprovalHandler.OnApprovedTx` 扣减部门预留池时：

```go
newReserved := reserved - personalBudgetAdded
if newReserved < 0 {
    newReserved = 0
}
```

并发竞态已经被 `AcquireBudgetLock` 解决，但锁内没有重新校验充足性，不足时静默 clamp 到 0 而不是报错拒绝。这意味着理论上可以让预留池"透支"而不报错——审批通过了，账却对不上。

**建议**：锁内重新判断 `reserved < personalBudgetAdded` 时直接返回 Validation 错误，而不是 clamp。

### 2.3 Toggle 与 Update 两条 Key 写路径的一致性策略不同

`UpdatePlatformKey` 是 DB-first + Sync + 失败回滚；`TogglePlatformKey` 是 Remote-first（先调 NewAPI，成功后写本地，本地写失败无回滚）。同一个资源的两个操作用了两种不同的一致性策略，出故障时排查成本高。

**建议**：统一策略。既然 `UpdatePlatformKey` 已经证明 DB-first + 回滚可行，`TogglePlatformKey` 也改成同样模式最省事。

### 2.4 Keys 域整体缺少统一的并发保护层

`SetPlatformKeys` 全量 load → 内存改 → 全量写回，这个模式在 `platform_key_create.go`、`platform_key_update.go`、`platform_key_actions.go` 里各自重复，没有统一的 advisory lock。Budget 域已经有 `AcquireBudgetLock` 这个模式，Keys 域没有对应物。

**建议**：短期给这几个直接 CRUD 路径都加锁；长期考虑把 `SetPlatformKeys`（全量覆盖）换成增量 API（`InsertKey`、`UpdateKeyStatus`），从根上消灭这类问题——全量覆盖模式天生就是并发不安全的。

## 3. Gateway 状态码语义

当前所有 precheck 失败（key 不存在、预算耗尽、模型不允许）统一返回 403，调用方无法区分原因来自我调决策。PRD 期望的语义是 401（key 无效）/ 403（模型不允许）/ 429（超限）/ 502（供应商不可用），限流部分已经正确走了独立的 429 路径，precheck 内部这几种情况没有分开。

**建议**：`Evaluate()` 的返回结构里加一个错误分类字段（比如 `ErrKind`），handler 层根据分类映射状态码，而不是所有 precheck 错误笼统 403。这个改动收益是双重的：调试体验更好，也顺便解决了下面安全部分提到的"信息不对称导致调用方无法区分是暂时限流还是永久拒绝，从而无法正确重试"的问题。

---

## 4. 通知投递的隐性降级

预算预警、超限阻断、组织同步保护三类事件在构造时都**硬编码** `Metadata.Priority = normal`，而不是按事件严重程度动态设置。`normal` 对应的 fallback 链只有 `[InApp]`，导致这三类事件即使 Email/SMS 渠道配置齐全，实际也只投递站内通知——代码"看起来"支持多渠道，运行时"实际"只走一条。

这类问题比功能缺失更隐蔽：测试的时候如果只看代码逻辑很容易误判为"已实现"，只有真的跑一遍才会发现渠道没生效。

**建议**：
1. 按事件严重程度设置 Priority（超限阻断至少应该是 `high` 甚至 `critical`）
2. 在 CI 或集成测试里加一条断言：关键业务事件（超限、预算预警）分发时检查 `resolvedChannels` 是否命中了 InApp 以外的渠道，防止这类"代码有但运行时没用上"的问题再犯

---

## 5. Store 层扩展性

`KeysRepository.PlatformKeys()` 是全量 load 到内存后再做筛选/分页/enrich，注释里也写明了"returns ALL keys"。当前公司数量下问题不大，但这是一个已知的规模化天花板——`apps/docs/plan/plan.md` §7 已经定义了触发阈值（`platform_keys` > 500 行或 P99 > 300ms），目前尚未触发。

**建议**：不需要现在做，但建议在监控里加一个 `platform_keys` 表行数的定期检查，接近阈值时提前排期，而不是等到线上变慢才发现。

---

## 6. 工程卫生（低风险，随手可修）

这些不影响正确性，但影响代码可读性和调用方体验，建议批量处理一次：

| 项 | 现状 | 建议 |
|---|---|---|
| `Void()` 响应 | 返回 `200 null` | 改 `204 No Content` |
| `response.JSON` 编码失败 | `_ = json.NewEncoder(w).Encode(v)` 静默忽略 | 先 `Marshal` 校验，失败写 500 |
| `DecodeJSON` | `http.MaxBytesReader(nil, ...)` 传 nil writer，超限不会自动断连 | 传入真实 `w` |
| CORS 中间件 | `Allow-Methods`/`Allow-Headers` 始终无条件设置，不管 Origin 是否命中白名单 | 仅在 Origin 匹配时设置 |
| `parseBearerSecret` | 只匹配大写 `"Bearer "` | 用 `strings.EqualFold` 前缀匹配（RFC 7235 要求 scheme 大小写不敏感） |
| `Delayer.Wait` | 300-500ms 模拟延迟散布在 10+ 个 domain 方法里 | 挪到 HTTP 中间件统一处理，domain 代码里少这些噪音 |

## 7. 文档与代码的一致性维护

这次审查发现有 3 份早期设计文档（`docs/plan/architecture-design.md`、`docs/plan/private-deployment.md`、`docs/plan/sms-pricing-architecture.md`）描述的架构方案已经被后来的实现完全取代或废弃，但文档本身还挂在仓库里没清理，容易让后来者误读为"计划中的方向"。已经在文档里加了醒目的"已被取代"说明，但建议后续直接归档删除，而不是留着当"历史参考"——过时的架构文档比没有文档更危险，因为它看起来权威。

---

## 8. 跨产品共享代码机会

`docs/shared-packages-analysis.md` 分析过 `apps/frontend` 和 `sms/frontend` 之间的重复代码（`cn()` 工具函数、React Query 基础设施、HTTP 客户端内核），给出的建议至今没有落地——`packages/ui-utils` 目录已创建但是空的，`packages/query`、`packages/api-core` 还没建。

这不是紧急的事，但如果两个前端还要继续并行演进，这部分重复会越滚越大。建议按文档里的优先级顺序（`ui-utils` 成本最低，`api-core` 因认证策略不同成本最高）在合适的时间窗口做掉第一阶段。

---

## 9. 不建议做的事（明确排除）

- **不建议**把 `internal/http/handler/platform/` 重构成独立的 `internal/platform/` 子树（`docs/plan/architecture-design.md` 早期设想过）。当前扁平结构工作得很好，没有实际痛点驱动这次重构，属于为了"看起来更规范"而增加复杂度。
- **不建议**现在就做 Store 层的 SQL 筛选/分页改造（第 5 节），除非真的触发了阈值——过早优化会引入不必要的复杂度和风险。
- **不建议**为了修复 `SetPlatformKeys` 并发问题而重写整个 Keys 域为 event sourcing 或类似的重架构，加锁 + 增量 API 足够解决问题。
