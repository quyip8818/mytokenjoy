# 计费安全 — 客户"薅羊毛"攻击面分析

> 专项审查：客户是否可能不付费或少付费使用 LLM 资源。  
> 所有结论基于代码阅读验证，附文件路径。

---

## 结论摘要

| 风险等级 | 攻击向量 | 影响 | 可利用难度 |
|---------|---------|------|-----------|
| 🔴 高 | 预检通过→入账前并发窗口（免费调用） | 每次请求可"透支"一次 LLM 调用 | 低（单次 curl 即可触发） |
| 🔴 高 | Overdraft 无上限，永远成功 | 余额耗尽后可无限调用 | 低（持续调用即可） |
| 🟠 中 | Precheck 缓存 5 分钟 + Ingest 不失效缓存 | 余额已为 0 后仍可在缓存窗口内调用 | 低 |
| 🟠 中 | 限流 fail-open | Redis 故障期间无限制 | 需先让 Redis 不可用（中等） |
| 🟡 低 | NewAPI token unlimited quota，不参与预检 | NewAPI 层不做任何拦截 | 低（但有 Gateway 和 Ingest 兜底） |

---

## 🔴 问题 1：预检通过→入账前的并发超卖窗口

### 机制

```
请求 1 → Gateway precheck (wallet=100, remain=50) → 通过 → 转发到 NewAPI → 响应返回
请求 2 → Gateway precheck (wallet=100, remain=50) → 通过 → 转发到 NewAPI → 响应返回
...
Ingest (几秒~分钟后)：请求 1 入账 → wallet=50
Ingest (稍后)：请求 2 入账 → wallet=0 (或 overdraft)
```

**Gateway 预检是"快照读"（PG 一次查询 + LRU 缓存 5 分钟），不是"预留扣减"。** 预检通过后到 Ingest 扣费之间有一个时间窗口（几秒到几分钟，取决于 NewAPI→webhook→River job 入队→Worker claim→执行的链路延迟），在这个窗口里**任意多的并发请求都会通过预检**，即使它们的累计消耗已经远超余额。

### 代码证据

- `gateway_service.go` → `precheck.Run()` → `PrecheckCache.Get()` → LRU 缓存 TTL 5min（`DefaultCacheTTL = 5 * time.Minute`，`precheck_cache.go`）
- `evaluate.go`：`WalletRemainQuota < minWalletQuota`（`minWalletQuota = 1`）只检查当前快照值
- Ingest 扣费（`ingest.go`）走 `store.WithTx` + `Company().LockForUpdate` + `ConsumeLots`，是**异步**发生的（webhook → River job → Worker claim → 执行）
- **Ingest 扣费后不会 `InvalidateCompany`**（搜索 `domain/usage` 下无任何 `InvalidateCompany` / `InvalidateByKeyID` 调用）——PrecheckCache 里的 `WalletRemainQuota` 只等 5 分钟 TTL 自然过期

### 影响

| 场景 | 影响 |
|------|------|
| 客户余额 ¥1，单次调用消耗 ¥0.5 | 在入账前可发起任意多次请求（假设 20 并发 × ¥0.5 = ¥10，实际只付了 ¥1） |
| 客户余额 ¥0（应该被拒绝） | 缓存窗口内仍能通过预检（缓存值仍 > 0） |
| 恶意客户故意并发冲刺 | 在 Key 被 OverrunService 封禁前（异步检查），可以积累大量未付费调用 |

### 为什么"Overdraft 兜底"不是好答案

虽然 `consumeLotsWithCompany` 在余额不足时会 `ExpandOverdraftLot`（下面详述），但这只是把"客户欠钱"记在账上——**如果客户就是不付**，你已经垫了供应商的成本。Overdraft 是"赊账机制"而非"防盗机制"。

## 🔴 问题 2：Overdraft 无上限，永远成功

### 机制

```go
// billing/lot/consume.go 第 90 行
if remaining > 0 {
    // 所有正常 lot 都耗尽了
    overdraftAdded = remaining
    od, err := st.Billing().ExpandOverdraftLot(ctx, companyID, currency, remaining)
    // 永远成功，没有任何上限检查
}
```

`ExpandOverdraftLot`（`billing_repo_lots.go` 第 66 行）：如果已有 overdraft lot，直接 `quota_granted += quotaDelta, quota_remaining += quotaDelta`；如果没有，新建一个。**没有任何上限、没有审批、没有告警阈值**。

### 攻击路径

1. 客户正常使用到余额为 0
2. OverrunService **异步**检测到 `consumed >= budget` 后封禁 Key
3. 在封禁生效前（窗口 = 问题 1 的并发窗口），客户发起的请求仍然会通过 Gateway 预检
4. Ingest 扣费时余额已为 0 → 走 overdraft → 无限扩展 → 计入"欠款"
5. 客户此时停止调用。你手里有一笔无上限的"应收账款"，但客户可能不付

### 为什么 OverrunService 不能完全阻止

OverrunService（`overrun.go`）是在 **Ingest 入账后异步判断**"consumed >= budget → 禁用 Key"。判断和执行之间又有延迟：

```
Ingest 同事务写 budget_consumed
→ 可选入队 overrun job（ShouldEnqueueOverrun，仅 combined_key_remain <= 0 时）
→ River claim + 执行
→ OverrunService.evaluateOverrun (重新锁公司、重新查 consumed)
→ keyControl.DisablePlatformKey (调 NewAPI 禁用 token)
```

在"入账→Key 禁用"之间的所有请求都会继续通过 Gateway（因为 Key 还是 active、budget cache 还未刷新）。

## 🟠 问题 3：PrecheckCache 5 分钟 TTL + Ingest 不主动失效

### 机制

`PrecheckCache`（`precheck_cache.go`）是 LRU + TTL 5 分钟。缓存的字段包括 `WalletRemainQuota`。

**以下场景会主动 `InvalidateCompany`**：
- 公司状态变更（freeze/suspend）—— `company/service.go` 第 152 行
- 公司升级（trial→standard）—— `company/service.go` 第 194 行
- 模型白名单变更 —— `models/service.go` 第 395 行

**以下场景不会主动失效**：
- **Ingest 扣费后 `WalletRemainQuota` 变化** — 不触发任何 `InvalidateCompany`
- **OverrunService 禁用 Key 后** — 调用 `keyControl.DisablePlatformKey`，但没有搜索到对应的 `InvalidateByKeyID`（注意：`keys/platform_key_actions.go` 的 `TogglePlatformKey` 里有 `s.cacheInvalidator.InvalidateByKeyID(id)`，但 Overrun 走的是 `port.OverrunKeyControl.DisablePlatformKey`，这条路径没有回调到 keys domain 的 cache invalidator）

这意味着：**Key 被 OverrunService 禁用后，Gateway 预检缓存里的该 Key 状态仍然是 `active`，最多还能继续放行 5 分钟。**

### 代码证据

`budget/overrun.go` → `action.keys(ctx)` → `s.keyControl.DisablePlatformKey(ctx, keyID)`

`newapisync/sync.go`（实现 `OverrunKeyControl`）→ `DisablePlatformKey` → 调 NewAPI Admin API 改 token 状态为 disabled + 本地 `store.Keys().SoftDisablePlatformKey` → **没有调用 `PrecheckCacheInvalidator.InvalidateByKeyID`**

而 `keys/platform_key_actions.go` 的正常 `TogglePlatformKey` 路径里是有 `s.cacheInvalidator.InvalidateByKeyID(id)` 的——说明这是被遗漏了，不是有意设计。

### 影响

Key 被超限封禁后，攻击窗口还有最多 5 分钟（缓存 TTL）。对于高频 API 调用者（LLM embedding 场景，每秒几十个请求），5 分钟内可以产生数百到数千个"应计为 0 余额后的非法调用"。

## 🟠 问题 4：Gateway 限流 fail-open

### 机制

`gateway_service.go` 第 160 行和 `middleware/rate_limit.go` 第 31 行：Redis 不可用时直接放行。

### 影响

如果 Redis 故障（或者恶意客户通过大量 Key + 高并发冲刷导致 Redis 连接耗尽），限流形同虚设。Per-key 限流默认 30 req/s burst 60，正常情况下限制了单次预检通过后的并发调用量；Redis 挂了之后这个阀门打开，问题 1 的窗口攻击效果成倍放大。

---

## 🟡 问题 5：NewAPI Token 是 unlimited_quota

### 机制

每个 Platform Key 在 NewAPI 侧对应的 token 被设置为 `UnlimitedQuota: true`（`newapisync/platformkey/create.go` 第 121 行）。这意味着 NewAPI 层本身**不做任何配额校验**——请求只要格式正确就会被转发到 LLM 供应商。

### 影响

配额管控全部依赖 TokenJoy 自己的 Gateway precheck + 异步 Ingest 扣费闭环。NewAPI 是"无脑透传"，不是兜底防线。这不是一个 bug（是有意设计——文档里明确写了"NewAPI token 为 unlimited_quota，Rebalance 只重算本地 combined_key_remain"），但意味着上面的问题 1-3 没有任何"下游二次防线"可以依赖。

## 🟢 已有的正面设计（不会被绕过的部分）

| 防线 | 机制 | 评价 |
|------|------|------|
| 入账幂等 | `ExistsIdempotency` 在 company lock 后检查 | 同一笔 log 不会重复扣费（正确） |
| Company lock | `LockForUpdate` 序列化所有 Ingest | 不会因并发 Ingest 导致超扣 lot（正确） |
| lot FIFO 消耗 | 正常 lot 耗尽后走 overdraft，不跳过 | 不会"凭空创造余额"（正确） |
| TJ passthrough + discount | `ApplyDiscount` 对 NewAPI 的 raw.Quota 乘以折扣系数，用 model_discount 表 | 客户不能通过篡改 NewAPI ratio 影响计费（正确；FullSyncToNewAPI 5min 兜底对齐） |
| Platform Key hash 验证 | Gateway 用 SHA-256(secret) 查 PG 确认 Key 有效性 | 不可能伪造有效 Key（正确） |
| 模型白名单 | 预检里确认 model 在 Key 的 allowlist 里 | 不能调用未授权的模型来规避高价定价（正确） |

## 修复建议

### 高优先（P0）：缩小并发窗口 + 限制 Overdraft 上限

#### 修复 A：Gateway 预检改为"乐观预留扣减"（最彻底但改动大）

预检通过时，用 Redis DECR（或 Postgres atomic decrement）从 `combined_key_remain` / `wallet_remain_quota` 预扣一个 `estimatedCost`。如果预扣后值 < 0，拒绝请求。Ingest 入账时用实际消耗值替换预扣值（差额回补）。

```
Gateway precheck:
  1. DECR combined_key_remain -= estimate → 如果 < 0 → 拒绝
  2. DECR wallet_remain_quota -= estimate → 如果 < 0 → 拒绝（回补上一步）
  3. 通过 → 反代 NewAPI

Ingest 入账:
  1. 计算实际 quota
  2. 差额 = actual - estimate
  3. 如果差额 > 0：再扣差额
  4. 如果差额 < 0：回补多扣的
```

**优点**：从根本上消灭并发超卖窗口
**缺点**：改动面大（Gateway 热路径引入 Redis 写操作 + 回补逻辑）、估价不准时有多扣/少扣的边界处理
**估工**：约 1-2 周

#### 修复 B：Overdraft 上限 + 超限立即断流（最快修复，推荐先做）

```go
// consume.go — ExpandOverdraftLot 前加检查
const maxOverdraftQuota int64 = 100000 // 运营可配置上限（如 ¥200 等价 quota）

currentOverdraft := getExistingOverdraftRemaining(ctx, st, companyID)
if currentOverdraft + remaining > maxOverdraftQuota {
    return ConsumeResult{}, domain.NewDomainError(402, "overdraft limit exceeded")
}
```

Ingest 扣费失败时（overdraft 超限），这笔 log 被标记为"rejected"而非"settled"——对应的 NewAPI 调用已经完成了（响应已返回给客户），但至少这个机制可以：
1. 让 OverrunService 更快触发（因为 Ingest 本身就报错，可以在同事务内直接禁 Key，不用等另一个异步 job）
2. 设置财务损失上限

**优点**：改动小（consume.go 加几行）、立即限制损失天花板
**缺点**：不能阻止"窗口内"的免费调用（只是限制了总量），已返回的 LLM 响应无法撤回
**估工**：1-2 天

#### 修复 C：OverrunService 封禁后主动失效 PrecheckCache（bug fix，应立即做）

在 `newapisync` 的 `DisablePlatformKey` 实现末尾（或在 `OverrunService.evaluateOverrun` 的 `action.keys(ctx)` 成功后），加一行：

```go
s.cacheInvalidator.InvalidateByKeyID(keyID)
```

需要把 `PrecheckCacheInvalidator` 注入到 OverrunService 或 NewAPISync 的 `DisablePlatformKey` 路径。

**效果**：Key 被超限封禁后，下一次 Gateway 请求必须重新从 PG 加载（会看到 Key 状态已变为 disabled），消灭"封禁后仍能调用 5 分钟"的窗口。

**估工**：半天

#### 修复 D：Ingest 扣费后刷新 PrecheckCache 的 WalletRemainQuota

在 `ingest.go` 的 post-commit 部分（已有 `RefreshCombinedKeySummaries`、`CheckBudgetAlerts` 的地方），加一行 `InvalidateCompany(companyID)`——让下次 Gateway 预检重新加载 wallet 余额。

```go
// ingest.go post-commit 部分补充
s.cacheInvalidator.InvalidateCompany(companyID)
```

需要给 `IngestService` 注入 `PrecheckCacheInvalidator`（目前没有注入）。

**效果**：钱包余额变化后，Gateway 立即能看到最新值（而不是等 5 分钟 TTL）。注意这不是完美防线（并发请求可能在同一毫秒同时通过），但至少能把窗口从"5 分钟"缩小到"单次 Ingest 处理延迟"。

**估工**：半天

---

### 推荐执行顺序

| 顺序 | 修复 | 效果 | 工作量 |
|------|------|------|--------|
| 1 | C（Overrun 封禁后失效缓存） | 消灭"封禁后 5 分钟仍可调用"窗口 | 0.5 天 |
| 2 | D（Ingest 后失效 wallet 缓存） | 把超卖窗口从 5 分钟缩小到 Ingest 延迟 | 0.5 天 |
| 3 | B（Overdraft 上限） | 限制最大损失天花板 | 1-2 天 |
| 4 | A（预留扣减） | 从根本上消灭并发超卖 | 1-2 周 |

修复 C 和 D 是 **bug fix**（遗漏了缓存失效），几乎无风险，建议立即做。

修复 B 是 **策略选择**（多大的 overdraft 上限可接受），需要产品决策。

修复 A 是 **架构升级**，需要考虑估价精度、回补逻辑、Redis 写操作对热路径延迟的影响，建议作为下一个迭代的专项。

## 实际风险评估

现阶段项目未上线（`DEPLOY_ENV=production` 的 `validateProductionContract` 路径还没跑过真实流量），这些问题还不会造成实际损失。但**一旦上线并有外部客户使用**，问题 1 和 2 的组合就是一个确定性的、无需任何技巧即可利用的"免费调用"通道：

1. 客户余额快要为 0 时
2. 用脚本并发发起大量请求（哪怕只是 `for i in {1..100}; do curl ... &; done`）
3. 所有请求都会通过 Gateway 预检（因为此刻缓存里的余额还 > 0）
4. 后续 Ingest 扣费时余额已为 0 → 走 overdraft → 客户不付账 = 你垫了供应商成本

这不需要任何"黑客技术"——只需要客户在余额即将耗尽时加速调用即可。甚至不需要恶意意图：正常的 batch embedding 场景（一次性发几百个并发请求处理文档）本身就会自然触发这个窗口。
