## 🔴 高风险

### 1. `www.tokenjoy.me` 无法正常 iframe 嵌入认证页（功能性配置错误，非纯安全问题）

**位置**：`deploy/nginx.conf`（3 个 server block 均设置 `add_header X-Frame-Options SAMEORIGIN always`）

**问题**：官网认证流程设计是 `www.tokenjoy.me` 通过 `<iframe src="https://app.tokenjoy.me/embed.html">` 嵌入登录/注册表单（见 `web/src/shared/Navbar.tsx`、`apps/frontend/src/embed-main.tsx`）。但 `app.tokenjoy.me` 的 nginx 响应头是 `X-Frame-Options: SAMEORIGIN`，这在严格遵循该 header 的浏览器里会**直接拒绝**跨子域 iframe 嵌入——`www.` 和 `app.` 是不同 origin，`SAMEORIGIN` 明确排除这种场景。

现代浏览器实际优先读 `Content-Security-Policy: frame-ancestors`，仓库里没有配置这个头，所以行为取决于浏览器对 `X-Frame-Options` 的处理策略，有埋雷风险（不同浏览器、不同版本表现可能不一致）。

**建议**：把 `frame-ancestors https://www.tokenjoy.me` 加到 CSP，并把 `app.tokenjoy.me` 的 `X-Frame-Options` 从全局 `SAMEORIGIN` 改为不设置（用 CSP 替代），或者只对 `/embed.html` 路径单独放行。

### 2. 邀请 Token 的 MAC 长度不足，且校验端点无频率限制

**位置**：`apps/backend/internal/pkg/invitetoken/invitetoken.go`、`apps/backend/internal/http/handler/auth/handler.go` 的 `GET /auth/invite-info`

**问题**：
- 邀请 token 用 XOR + HMAC-SHA256 方案，**MAC 只截断到 4 字节（32 bit）**。文件注释里已经写明这是为了短信字符数限制做的妥协设计（`ponytail: intentionally compact for SMS constraints`），有说明升级路径（AES-GCM），但目前未升级。
- `GET /auth/invite-info?code=<token>` 是查询邀请信息的公开端点，**不在** `RateLimitLoginPaths` 覆盖范围内——该中间件只匹配 `POST` 方法（`RateLimitLoginPaths` 实现里 `if r.Method == http.MethodPost`），而这是 `GET`。同时该请求未鉴权，`RateLimitTenant` 在 `companyID == uuid.Nil` 时直接 skip，等于这个端点**完全没有速率限制**。
- 端点对不同失败原因返回不同状态码（400 "invalid or expired invite token" = MAC 校验失败；404 "invite not found" = MAC 通过但邀请码不存在），这构成一个可用的 oracle。

**影响**：32-bit MAC 理论上可以通过在线枚举以约 2^31 次尝试的期望值伪造出一个能通过校验的 token（生日攻击意义上的"任意可通过校验的密文"，不是针对特定明文的原像攻击）。因为端点无速率限制，攻击者可以并行发起请求进行离线预计算辅助的在线验证。这不是"几秒钟就能破解"的量级，但也不是可以放心忽略的强度——尤其邀请 token 一旦伪造成功，`AcceptInvite` 流程允许**未登录用户**用邀请码 + 自定义密码直接创建账号并加入对应企业（`domain/company.Service.AcceptInvite`）。

**建议**：
1. 短期：给 `GET /auth/invite-info` 也套上速率限制（哪怕比 POST 的阈值宽松一点）
2. 中期：把 MAC 从 4 字节升到至少 8-16 字节。如果字符数预算紧张，可以牺牲一点长度换安全（比如把 base64url 输出从 18 字符放宽到 24-26 字符，短信模板里大多数场景可以接受）
3. 不建议无脑换 AES-GCM——文档里"升级路径"提到的方案会让 token 变到 50+ 字符，对短信渠道不友好，需要产品侧先确认这个约束是否还存在

## 🟠 中风险

### 3. Gateway per-key 限流与 tenant 限流均为 fail-open

**位置**：`domain/gateway/gateway_service.go` `checkRateLimit`、`middleware/rate_limit.go` `RateLimitTenant`

**问题**：Redis 不可用时，两处限流都直接放行请求（"优先可用性"的设计选择，代码注释里写明是有意为之）。这是合理的可用性权衡，但意味着 Redis 故障期间实际上等于**无限流保护**，如果同时发生 Redis 故障 + 恶意流量，防线会同时失效。

登录限流（`RateLimitLogin`）是 fail-closed（Redis 挂了会 fallback 到内存限流器），这条路径设计是对的，只是内存限流器是单实例内存态，多副本部署下各实例各算各的，等效阈值会随副本数放大。

**建议**：
- Gateway/Tenant 限流保持 fail-open（这里业务权衡是对的，可用性优先于严格限流），但建议加一条监控告警：Redis 限流器错误率超过某阈值时报警，让人知道"此刻限流实际上不生效"，而不是完全沉默地降级
- 内存限流器多副本放大的问题记录为已知限制，不建议现在改（除非已经是多副本部署且限流是硬需求）

### 4. Webhook 认证依赖单一静态 Secret，无签名防重放

**位置**：`http/handler/ingest/handler.go` `authenticateWebhookSecret`

**问题**：NewAPI → Backend 的消耗结算 webhook（`POST /api/internal/webhooks/newapi-log`）用固定 header `X-Webhook-Secret` 常量时间比较校验（`subtle.ConstantTimeCompare`，防时序攻击这块做对了）。但没有请求签名（如 HMAC over body + timestamp）、没有防重放机制。如果 secret 泄露（比如日志误打），攻击者可以重放旧请求或伪造任意消耗记录。

**影响范围有限**：这个端点只有内网可达（`NEW_API_BASE_URL` 是内网地址，NewAPI 不对外暴露），泄露路径主要是配置/日志层面的疏忽，不是公网直接可达的攻击面。但作为计费相关的关键端点，伪造/重放的后果是"多计费或少计费"，属于财务相关面。

**建议**：如果短期不改造签名机制，至少确保 `NEW_API_WEBHOOK_SECRET` 不出现在任何日志输出里（当前没发现有打印，但建议加一条 CI 检查防止未来引入）。中期可以加时间戳 + HMAC 签名，防止 secret 泄露后被无限重放。

### 5. `parseBearerSecret` 大小写敏感

**位置**：`domain/gateway/auth.go`

**问题**：Gateway 只匹配大写 `"Bearer "` 前缀，RFC 7235 规定 auth-scheme 大小写不敏感。不算安全漏洞，但是个标准符合性问题——如果调用方用小写 `bearer` 会被拒绝，容易被误判为"认证失败"而不是"格式问题"，增加排查成本。

**建议**：改成 `strings.EqualFold` 或大小写不敏感前缀匹配。

## 🟡 低风险 / 已确认无问题（记录以避免重复排查）

### 6. SSL 私钥文件正确排除在版本控制外

**位置**：`deploy/ssl/www.tokenjoy.me.key`（本次对话打开的编辑器文件之一）

**核实结果**：该文件路径匹配 `.gitignore` 第 61 行的 `deploy/ssl/*.key` 规则，`git ls-files` 确认仓库里 `deploy/ssl/` 下**只跟踪了一个 `.gitkeep`**，私钥文件本身从未被提交。这是正确的做法，无需处理。

### 7. 已提交的 `.env.development` 文件只含本地开发占位符

**位置**：`apps/backend/.env.development`、`apps/frontend/.env.development`、`web/.env.development`

**核实结果**：这三个文件确实被 git 跟踪，但内容检查后确认只含本地开发用的占位密钥（如 `SESSION_SECRET=tokenjoy-dev-session-secret-local`、`PLATFORM_BOOTSTRAP_PASSWORD=admin1234`），不涉及真实凭证或生产密钥。生产部署走 `deploy/init.sh`，其中所有敏感值都用 `openssl rand` 现场生成并写入 `deploy/env/*.env`（这些文件本身在 `.gitignore` 里，未跟踪）。这个模式是对的。

### 8. JWT 签名算法固定校验，防 alg 混淆攻击

**位置**：`identity/sessiontoken/issuer.go`、`identity/registertoken/token.go`

**核实结果**：两处 JWT `Parse` 都在 keyfunc 里显式校验 `t.Method != jwt.SigningMethodHS256` 才返回签名验证用的 key，防止了经典的"algorithm confusion"攻击（攻击者构造 `alg: none` 或换成非对称算法诱导服务端用公钥当 HMAC key 验证）。这个实现是对的。

### 9. Cookie 属性设置正确

**位置**：`identity/httpx/token.go`

**核实结果**：Session cookie（`HttpOnly` + `SameSite=Lax` + 生产 `Secure`）、Refresh cookie（`HttpOnly` + `SameSite=Strict` + Path 限定到 `/api/auth/refresh` + 生产 `Secure`）配置均符合最佳实践。Refresh token 在 DB 里存的是 SHA-256 hash（不是明文），泄库也不能直接拿去用。

### 10. 生产环境配置有 fail-fast 校验

**位置**：`config/deploy.go` `validateProductionContract`

**核实结果**：`DEPLOY_ENV=production` 时启动会强制校验 `SECURE_COOKIE=true`、`NEW_API_WEBHOOK_SECRET` 非空、`SIMULATE_DELAY=false`、`SKIP_VERIFY_CODE=false` 等一批"生产不该有的开发态配置"，任一项不满足直接拒绝启动。这个 fail-fast 设计能防止很多"开发配置误带上生产"的事故，是加分项。

### 11. CORS 白名单严格，非通配符

**位置**：`config/config.go` `CORSOriginList()`、`middleware/cors.go`

**核实结果**：CORS 是显式 origin 白名单比对（`originSet[origin]`），不是 `Access-Control-Allow-Origin: *`。生产环境每个域名（`app.tokenjoy.me`/`sms.tokenjoy.me`）单独配置。这个实现是对的，唯一的小问题是 `Allow-Methods`/`Allow-Headers` 头在 Origin 不匹配时也会被设置（已记录在架构优化建议文档里，是工程卫生问题不是安全漏洞——因为没有 `Access-Control-Allow-Origin` 时浏览器不会真正放行跨域请求）。

### 12. 验证码校验有防暴力破解机制

**位置**：`identity/verifycode/service.go`

**核实结果**：验证码校验有失败次数上限（`maxAttempts = 5`，15 分钟锁定窗口）、发送频率限制（60 秒发送间隔 + 每日 10 次上限），这套机制设计合理，覆盖了短信/邮箱验证码场景下的常见暴力破解和骚扰发送风险。

## 需要产品/运营侧关注但非代码问题

- **Gateway 超限返回 403 而非 429**（PRD 期望 429）：这不是安全漏洞，但如果有对外 SLA 或调用方依赖标准 HTTP 语义做重试逻辑，语义不一致可能导致调用方误判为"永久拒绝"而放弃重试，等同于服务可用性问题。详见架构优化建议文档 §3。
- **通知优先级硬编码**导致预警/超限实际只投递站内通知：如果客户依赖 Email/SMS 预警来感知预算超支，这是一个"看起来配置好了但实际不生效"的信任缺口，建议尽快修（详见架构优化建议文档 §4）。

## 本次审查的边界

本次审查基于静态代码阅读（grep + 读文件），**不包含**：
- 依赖包已知漏洞扫描（建议单独跑 `govulncheck` / `pnpm audit`）
- 动态测试（渗透测试、fuzzing）
- 生产环境实际部署配置核查（本次核对的是 `deploy/` 目录下的模板/脚本，不是线上实际运行的配置）
- NewAPI 上游代码本身的安全性（本项目对 NewAPI 打了 4 个 patch，patch 本身逻辑已核对，但 NewAPI 主体代码未做安全审计）
