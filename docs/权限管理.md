# 权限管理指南

> **架构**：Identity Token + 应用内 PDP 请求时刻求值  
> **读者**：后端 / 前端开发

---

## 1. 架构总览

```
请求 → Cookie/Bearer JWT → RequireSession（parse + PDP 求值）→ RequireAnyPermission → Handler
```

核心原则：

- Token **仅含 identity**（`sub`=memberID, `company_id`, `sid`, `exp`），**不含** permissions/roles
- 授权在 **服务端 PDP 每请求求值**；UI 不展开角色
- Capability 以 `packages/contracts/permission/manifest.json` 为 **唯一真相**
- UI 首屏调一次 `GET /api/session` 获取权限列表，之后内存判断

## 2. 认证（AuthN）

### 2.1 Session JWT

| Claim | 说明 |
|-------|------|
| `sub` | `members.id` |
| `company_id` | 租户 ID |
| `user_id` | 关联 users 表（可选） |
| `sid` | 会话 ID |
| `iat`/`exp` | 签发/过期时间 |

签名算法 HS256，密钥 `SESSION_SECRET`，TTL 由 `SESSION_TTL_SEC` 控制（默认 900s）。

Cookie 名：`tokenjoy_session_member`（HttpOnly, SameSite=Lax, Secure）。  
Bearer：`Authorization: Bearer <jwt>`，与 Cookie 等价，同一 parse 逻辑。

**禁止**在 token 内放 permissions、roles。

### 2.2 公开端点

| 端点 | 行为 |
|------|------|
| `POST /api/auth/login` | 校验密码 → 签发 JWT → Set-Cookie |
| `POST /api/auth/logout` | 清 Cookie |
| `POST /api/auth/accept-invite` | 激活成员 → 签发 JWT |
| `POST /api/auth/refresh` | Refresh token 换新 Access token |

### 2.3 平台面

独立 Cookie `tokenjoy_platform_session`，独立密钥 `PLATFORM_SESSION_SECRET`。  
不走企业 RBAC PDP。

## 3. 授权（AuthZ）

### 3.1 组件

| 组件 | 包 | 职责 |
|------|---|------|
| **PIP** | `store/org` | `GetMemberAuthz(companyID, memberID)` → member + roles |
| **PDP** | `identity/authz` | `ResolveMemberPermissions` → `[]capability` + `readOnly` |
| **PEP-Session** | `middleware/session` | Parse JWT → 租户校验 → `GetSessionContext` |
| **PEP-Authz** | `middleware/authz` | `HasAny(permissions, required...)` — OR 语义 |
| **PAP** | `domain/org` | 角色 CRUD，变更时 bump `authz_revision` |

### 3.2 请求时刻流程

```go
// middleware/session.go
claims := httpx.ParseMemberToken(r, issuer)         // 1. 解析 JWT
sessionCtx := authzSvc.GetSessionContext(ctx, claims.CompanyID, memberID) // 2. PDP 求值
// → 内部: revision 缓存(5s TTL) → LRU 缓存(companyID+memberID+revision)
// → cache miss: store.Org().GetMemberAuthz → ResolveMemberPermissions

// middleware/authz.go
authz.HasAny(sessionCtx.Permissions, required...)   // 3. OR 判断
```

### 3.3 权限展开规则

`identity/authz/resolve.go`：

1. 遍历成员所属角色
2. **Preset 角色**：从 manifest `presetRoles` 查表展开（`*` = 全部 capabilities）
3. **Custom 角色**：按 DB 存的 `p-*` ID 经 manifest `permissionIdMap` 映射为 capability 字符串
4. **隐式规则**：拥有任一 `budgetWriteCapabilities` → 自动附加 `budget:read`
5. `readOnly`：无 manifest `writeCapabilities` 中任一项时为 true

### 3.4 `authz_revision` 缓存失效

PDP LRU cache key = `(companyID, memberID, revision)`。  
任何改变授权图的操作（角色 CRUD、成员-角色绑定变更、成员禁用等）在事务内 bump `companies.authz_revision`。  
revision 变化使该租户所有缓存 entry miss。

## 4. 路由注册指南

### 4.1 中间件工具（`middleware/routes.go`）

```go
// 仅 Session（不要求 capability）
middleware.SessionRoutes(r, p)

// Session + 读 capability
middleware.ReadRoutes(r, p, "org:read")

// 在 ReadRoutes 基础上追加写 capability
sub := middleware.ReadRoutes(r, p, "org:read")
sub.With(middleware.RequireAnyPermission("org:structure")).Post("/departments", handler)
```

**`RequireAnyPermission(a, b)` = OR**：拥有 a 或 b 任一即通过。不存在 RequireAll。

### 4.2 路由分类

| 分类 | 行为 |
|------|------|
| 公开路由 | 无 Session：login/logout/accept-invite/healthz/webhook |
| Session only | `GET /api/session`（返回 SessionContext） |
| 业务路由 | Session + `RequireAnyPermission(capabilities...)` |

### 4.3 新增端点步骤

1. 确认需要哪个 capability（查 manifest.json `capabilities` 列表）
2. 在 handler 注册时用 `ReadRoutes` 或 `SessionRoutes` + `RequireAnyPermission`
3. 如需新 capability → 先加到 `manifest.json` 再 `pnpm generate:permissions`

## 5. 单一契约：manifest.json

路径：`packages/contracts/permission/manifest.json`

生成物：
- `apps/backend/internal/infra/permission/keys.go`（`go:embed`）
- `apps/frontend/src/lib/permission-keys.ts`

### 5.1 结构

```jsonc
{
  "capabilities": ["org:read", ...],          // 全部 capability 字符串
  "permissionIdMap": { "p-1": "org:structure", ... }, // DB p-* → capability
  "presetRoles": { "超级管理员": ["*"], ... },       // 预设角色 → capabilities
  "writeCapabilities": [...],                 // 写能力集合（用于判断 readOnly）
  "budgetWriteCapabilities": [...],           // 预算写（触发 budget:read 隐式规则）
  "rules": { "budgetWriteImpliesRead": true }
}
```

### 5.2 变更流程

1. 编辑 `packages/contracts/permission/manifest.json`
2. 运行 `pnpm generate:permissions`（生成 `keys.go` + `permission-keys.ts`）
3. 后端 / 前端分别使用生成的常量
4. CI `pnpm check:permissions` 校验三方一致

## 6. 前端权限指南

### 6.1 Session 加载

```
App mount → AuthSessionProvider → GET /api/session → SessionReactContext
```

返回 `SessionContext` 包含 `permissions[]`、`readOnly`、`authzRevision`。

### 6.2 权限判断 API

```tsx
import { usePermissions } from '@/features/session'

function MyComponent() {
  const { has, canWrite } = usePermissions()
  
  if (!has('budget:read')) return null          // 组件显隐
  return <Button disabled={!canWrite}>操作</Button>  // 写操作
}
```

路由级：`routes.ts` 中 `requiredPermissions` 声明（OR 语义），`canAccessRoute` 自动判断。

### 6.3 Session 刷新策略

| 触发 | 行为 |
|------|------|
| 响应头 `X-Authz-Revision` > 当前 revision | `refreshSession()` |
| `window.focus` 且距上次 > 60s | `refreshSession()` |
| `BroadcastChannel('tokenjoy-authz')` 消息 | `refreshSession()` |
| 业务 API 返回 403 | `refreshSession()` 一次 |
| PAP mutation 成功（角色/成员变更） | 调用 `broadcastAuthzChange()` |

**禁止**：per-component 调 session API；localStorage 存 permissions。

### 6.4 新增页面步骤

1. 在 `routes.ts` 添加 `RouteDefinition`，填 `requiredPermissions`
2. 使用 `PERMISSION` 常量（来自生成的 `permission-keys.ts`）
3. 页面内用 `usePermissions().has(...)` 控制细粒度显隐

## 7. RBAC 数据模型

```
members ↔ member_roles ↔ roles ↔ role_permission_grants ↔ permissions
```

- **Preset 角色**：名称固定（超级管理员、组织管理员、普通成员、只读审计员、API 调用者、平台管理员），展开由 manifest 决定
- **Custom 角色**：DB 存 `p-*` 引用，PDP 按 `permissionIdMap` 展开
- 角色名称 & ID 常量：`internal/domain/grants/roles.go`
